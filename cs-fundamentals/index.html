Why this list

Every lab is public and free.

Modules

Six tracks, twenty-three builds

You extend xv6 — a small teaching Unix — from simple userspace tools all the way to a multiprocessor kernel with virtual memory, copy-on-write, and a real NIC driver. It's the deepest, most literal way to understand what an operating system actually does underneath every syscall you've ever called.

  1. 01

    Unix utilities & syscalls

    You start by writing small Unix tools (a Xargs, a Find, a ping-pong pipe program) directly against xv6's syscall interface, then add two new syscalls yourself — a syscall tracer and a sysinfo call that reports kernel state. This is the on-ramp: it forces you to read the xv6 source before you touch anything that runs in kernel mode.

    arch=riscv64emu=qemu
    • →6.1810 course site
    • →xv6-riscv on GitHub
  2. 02

    Page tables & traps

    You print a process's page table, add a second address space to speed up syscalls, then work through how xv6 handles traps — the mechanism that switches from user mode to kernel mode on a syscall, interrupt, or exception. By the end you know exactly what "the CPU jumps into the kernel" means at the level of registers and the trapframe.

    • →pgtbl & traps lab handouts
    • →xv6 book, ch. 3–4
  3. 03

    Copy-on-write & locks

    fork() naively copies the entire parent address space — you rewrite it to share physical pages and only copy-on-write when either side writes. Then you go multiprocessor: replace xv6's coarse kernel lock with fine-grained locks in the allocator and buffer cache, and watch throughput actually scale with cores.

    • →cow & lock lab handouts
    • →xv6 book, ch. 6 — Locking
  4. 04

    File system, mmap & networking

    You extend the on-disk file system with larger files and symlinks, implement mmap() with lazy page-fault-driven loading, then write an E1000 NIC driver's transmit/receive paths — so the semester ends with your kernel talking to the outside world, not just to itself.

    • →fs, mmap & net lab handouts
    • →xv6 book, ch. 8 — File system
Open 6.1810 →

You build TCP/IP from the byte stream up: reassembly, the receiver, the sender, then ARP and IP routing — ending with a stack that can hold a real connection with an actual server on the internet.

  1. 01

    Byte stream & reassembly

    Checkpoint 0 has you write a tiny web crawler against the kernel's own TCP socket, then implement an in-memory reliable byte stream. Checkpoint 1 is the Reassembler: segments arrive out of order and can overlap or duplicate, and your job is to stitch arbitrary byte ranges back into one ordered stream.

    • →CS144 course site — checkpoints 0–7
    • →Beej's Guide to Network Programming
  2. 02

    TCP receiver

    You implement the receiving half of TCP: turning segments into calls on your Reassembler, tracking the 32-bit sequence-number space with wraparound, and reporting a correct window size back to the sender. This is where TCP's "reliable stream over an unreliable network" promise actually gets kept.

    • →TCP Receiver checkpoint handout
    • →RFC 9293 — the TCP specification
  3. 03

    TCP sender

    The sender decides when to send, what to send, and when to give up and retransmit — a timer that doubles on every consecutive timeout and resets once an ACK makes progress. Put receiver and sender together and you have a working, RFC-compliant TCP.

    • →TCP Sender checkpoint handout
    • →RFC 6298 — retransmission timer
  4. 04

    Network interface & router

    The last checkpoints drop a layer: a NetworkInterface translating IP datagrams to Ethernet frames via ARP, then an IP router forwarding by longest-prefix match. Finish this and you've implemented every layer between send() and a frame on the wire.

    • →Interface & IP Router handouts
    • →RFC 826 — ARP
Open CS144 →

You build out BusTub, the CMU Database Group's teaching DBMS — buffer pool, B+Tree index, query executors, and concurrency control — ending with a real, working relational database engine you wrote yourself.

  1. 01

    C++ primer

    Project 0 is a copy-on-write trie built under strict rules — no raw pointers, no locks, only shared_ptr and immutability — that must hit a perfect score before you're allowed to touch BusTub itself. It exists purely to filter out "I don't actually know modern C++" before it costs you a week on Project 1.

    • →15-445/645 course site
    • →bustub on GitHub
  2. 02

    Buffer pool manager

    Every database is bigger than RAM, so it needs a component that shuttles fixed-size pages between disk and an in-memory pool, tracking pinned vs. evictable pages, and picking a victim with an LRU-K policy when full. Get this wrong and every layer above it silently corrupts data.

    • →Project #1: Buffer Pool Manager
    • →CMU Database Group — lectures & papers
  3. 03

    B+Tree index

    A disk-based, thread-safe B+Tree — the structure almost every relational database uses for indexes — with point lookups, range scans, and concurrent inserts/deletes via latch crabbing. Students routinely say this project taught them more about real data structures than an entire algorithms course.

    • →Project #2: B+Tree Index
    • →Full assignments list
  4. 04

    Query execution & concurrency control

    Project 3 builds the Volcano-style iterator operators (scans, joins, aggregation, sorting) that turn a query plan into results. Project 4 makes it correct under concurrent transactions with two-phase locking or MVCC, so overlapping readers and writers can't corrupt each other's view of the data.

    • →Projects #3 & #4
    • →CMU Database Group on YouTube
Open 15-445 →

Two sibling courses (same lineage, taught at CMU and Stanford) that take you from a single multicore machine to a GPU to a cluster of machines — the performance layer underneath everything in tracks 01–03 and 05.

  1. 01

    Multicore & SIMD

    You parallelize small programs (a Mandelbrot renderer, a sqrt approximator) first with ISPC, which compiles to SIMD instructions across your cores, then with raw threads — graded partly on a speedup analysis, not just correct output. The fastest way to build intuition for why "more cores" isn't automatically "more speed."

    • →Stanford CS149 course site
    • →stanford-cs149 starter code
  2. 02

    Parallel task scheduler

    You build a task execution library from scratch in C++ — the same category of system as a game engine's thread pool — implementing scheduling policies for task graphs with dependencies, and measuring how overhead and load balancing trade off as task sizes shrink.

    • →Task scheduler assignment handout
  3. 03

    GPU programming

    A parallel renderer in CUDA — circles composited onto a canvas — that forces you to understand thread blocks, warps, shared memory, and memory coalescing, because a naive version is both wrong and slow at once. Most people's first real contact with how a GPU schedules work, underneath the CUDA/PyTorch abstractions used daily in ML.

    • →CUDA renderer assignment handout
    • →NVIDIA CUDA Programming Guide
  4. 04

    Large-scale parallel workloads

    Graph algorithms like PageRank or BFS, parallelized first with OpenMP on one machine, then with MPI across machines that share nothing and must communicate by message-passing. A deliberate bridge — the programming model here is exactly what track 05's distributed systems course is built on.

    • →Graph processing assignment handout
    • →CMU 15-418/618 course profile
Open CS149 →

The course this whole page bends toward: MapReduce, then Raft consensus, then a fault-tolerant and finally a sharded key-value store — where OS-level failure handling, network RPC, and database-level correctness under concurrency all get composed into one problem.

  1. 01

    MapReduce

    Implement a MapReduce coordinator and worker pool from the original Google paper: the coordinator hands out map/reduce tasks over RPC, and — the actual point of the lab — has to notice when a worker dies mid-task and re-assign it without corrupting output. The gentlest introduction to "things fail, and your system has to keep working anyway."

    • →6.5840 course site
    • →MapReduce — the OSDI '04 paper
  2. 02

    Raft consensus

    The heart of the course: implement Raft, the consensus algorithm behind etcd, CockroachDB, and Consul — leader election, log replication via AppendEntries, persistence, and log compaction via snapshots. Tests inject network partitions, dropped RPCs, and crashes at every stage; famously the hardest lab.

    • →In Search of an Understandable Consensus Algorithm
    • →The Secret Lives of Data — Raft, visualized
  3. 03

    Fault-tolerant KV store

    A key/value service on top of Raft: clients send Put/Append/Get to whichever server they believe is leader, the service submits each op to Raft and only applies it once committed on a majority. You also handle duplicate client retries without double-applying — where "distributed systems are hard" becomes a specific bug you're chasing.

    • →Lab 4: Fault-tolerant KV Service
  4. 04

    Sharded KV service

    Split the keyspace across independent Raft groups coordinated by a shard controller that can move ownership between groups while the system stays live — without ever losing a write or serving stale data mid-handoff. Essentially how CockroachDB or DynamoDB scale writes horizontally.

    • →Lab 5 & required paper readings

How the tracks actually connect

01
One fast, correct machine
Tracks 01–04
OS (how a single machine runs code) → Networking (how machines talk) → Databases (how to store and query data reliably) → Parallel/GPU (how to make all of the above fast on modern hardware). Each is a self-contained systems course you can do in any order once you have C/C++ and a Linux terminal.
02
Many machines, one system
Track 05 — and beyond
6.5840 composes OS-level failure handling, network-level RPC, and database-level correctness under concurrency into one problem: keep a service correct when machines crash and the network drops, delays, or reorders messages at any time. The electives are just more reps at that same problem.
